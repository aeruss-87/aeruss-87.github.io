A working setup, explained in detail

Files remember, chats forget

How I run my job with Claude across several apps without re-explaining myself every session. One folder of plain-text files that every session reads first and updates last, plus a set of written rules that tell Claude exactly what to update and where.

The core idea

I use Claude in several places at once: a few VS Code windows running Claude Code, the desktop app, claude.ai, and Cowork. None of those conversations can see each other, and any one of them can run out of context or get closed. So nothing important is allowed to live only in a chat. Every fact has exactly one home in a file, every session starts by reading the files, and every session ends by writing back to them.

The folder is an Obsidian vault, which is just a folder of Markdown files with [[wikilinks]] between them. Claude Code reads and edits the files directly. Obsidian Sync puts them on my phone, and I edit them myself between sessions, mostly by ticking checkboxes and jotting one-line notes.

The test for whether something is worth filing: would it change what Claude recommends next time? If yes, it gets one line in the right file. If no, it stays in the chat and is allowed to disappear.

The pieces

Each file answers one question. When Claude learns something, the question it answers tells Claude where it goes, and when Claude needs something, the question tells it where to look.

Outside the vault: Craft holds my session log and a "context hub" page, because claude.ai and Cowork can read Craft through a connector but can't reach files on my laptop. Notion is where finished work goes once it's ready for other people. New work always starts as a local draft and graduates.

How Claude knows what to do

Claude doesn't remember anything between sessions on its own. Everything it "knows" about this system is written down in one of five places, and each loads at a different moment.

LayerWhat it holdsWhen Claude reads it
Global CLAUDE.mdThe operating manual: who I am, the folder map, every trigger phrase and what it does, the logging procedure, writing rules, and how to push back on me.Automatically, at the start of every Claude Code session
Memory folderSmall files, one fact each: corrections I've made, preferences, gotchas. An index file (MEMORY.md) lists them in one line each.The index loads every session; Claude opens a memory when it looks relevant
SkillsStep-by-step procedures for recurring jobs: process meeting notes, run open loops, run the weekly sweep, write in my voice. Each has a description listing its trigger phrases.When what I type matches a skill's description
Folder schemasRules that govern one folder, like wiki/CLAUDE.md, which defines how pages are written, cited and linted.Before doing any work in that folder
TemplatesThe blank shape of a state file, a meeting note, each wiki page type, and (in Craft) a session log entry.When creating a new file of that type

So when I type log this session, nothing magic happens. Claude finds that phrase in CLAUDE.md, which says, in effect: update the state file first, ask me one or two status questions, read the template doc in Craft, write the entry, mirror it into the vault, screen it for the wiki and the ledger. It follows the written steps.

How the rules evolve

When something goes wrong, I correct Claude and the correction gets written into whichever layer owns it, in the same turn. A one-off fact goes to the file where the wrong version lived. A preference goes to memory. A procedure change goes into the skill or CLAUDE.md with a date ("rule set 2026-11-03"), so later sessions can tell which rule is newer when two seem to conflict. Most of the rules on this page exist because something broke once.

One meeting, traced through the system

The easiest way to see how the pieces link is to follow one input. Say I have a 1:1 with my manager about a role I'm hiring for. They agree to the level I proposed, ask me to send them the interview plan by Friday, and mention they prefer a one-page summary to a full doc. I also say I'm worried the timeline is too tight.

Granola records it. At the end of the day I say process granola, and the skill does this:

  1. Pull and file the note. The skill fetches the meeting from Granola through its connector and writes meetings/granola/2026-11-17 Manager 1on1.md with frontmatter: date, attendees as links to their wiki pages, the project as a link to its state file, and status: unprocessed.
  2. Routing gate. It checks whether the call belongs in this vault at all. Personal calls and side-project calls get moved to their own vaults and never touch work files.
  3. Write the summary sections above Granola's own summary: takeaways, decisions (with a verbatim quote when the wording matters, which it usually does for anything about level or money), to-dos, open items.
  4. To-dos go to the tracker. "Send the interview plan by Friday" becomes a new numbered line in Waiting on Me: - [ ] **412 Send interview plan to manager** · Fri · manager. One page. See [[hiring-state]].
  5. Project facts go to the state file. "Level agreed" overwrites the line in state/hiring-state.md that said "level proposed, awaiting manager." The old wording is gone; the meeting note is the history.
  6. My worry goes to My read in the same state file: - 2026-11-17: Timeline feels too tight for a real search.
  7. The proposal closes in the ledger. The row for "propose this level" moves from sent to accepted, with how it closed: "agreed orally in the 1:1."
  8. Person insight goes to their wiki page. Under Working with them: - 2026-11-17: Prefers a one-page summary over a full doc for hiring plans. ([[2026-11-17 Manager 1on1]])
  9. Durable knowledge goes to the wiki. If the level decision sets a precedent (what this level means for this kind of role), the concept page about levels gets updated, citing the meeting.
  10. Wiki bookkeeping. The meeting note gets a line listing which wiki pages were touched (or "checked, nothing new"), wiki/log.md gets an entry, and only then does the note flip to status: processed.

One 30-minute meeting, six files touched, and each fact is in the place a future session will look for it. Next morning, where do things stand? surfaces loop 412 as due Friday without anyone remembering the meeting.

How state files get updated

A state file is one project's current picture, readable in a minute. It's what a fresh session reads when I say resume hiring. The rule that made them work: a state file is a snapshot, not a log. New information overwrites what it supersedes, so the file always reads as now and stays around 10KB. History lives in meeting notes, session mirrors, and an archive copy made whenever a file is compacted.

state/hiring-state.md (shape)

# Hiring State: backfill for the office role
Last updated: 2026-11-17 (level agreed in manager 1:1)
Status: ACTIVE, level agreed, plan due Friday.

## Notes (unprocessed)   my inbox; Claude folds it in and empties it
## Purpose               why it exists, links to related projects
## Artifacts             what's canonical, plus Notion URLs, Slack
                        threads, Drive paths a search can't find
## Current state         real dates, real numbers, full names
## My read              dated lines: worries, leans, distrust
## Key facts, settled    decided; don't relitigate
## Next steps            a pointer to the tracker, never a list
## To resume             a paste-ready opener for a new session

What can touch a state file

  • update the files at the end of a working session
  • debrief: and file this: when I report something that happened
  • process granola when a meeting changed something material
  • The weekly open loops scan, which files project decisions it finds in Slack and email threads
  • The weekly state sweep
  • Me, directly: a ticked box, or a line dropped in Notes from my phone

What Claude does on every touch, in order

  1. Process ticked boxes. A - [x] anywhere means done or no longer needed. Claude reconciles the prose around it and every other file that item lives in.
  2. Empty the Notes section. Each line I jotted gets folded into its real home (Current state, Key facts, My read, the tracker, or the ledger), and the section is cleared. Empty Notes means the file is caught up.
  3. Fold in the new information. Rewrite the relevant lines of Current state or Key facts and overwrite what's superseded. Never append a dated "Update" block.
  4. Send actions elsewhere. Anything that's a next step goes to the tracker's Project next steps section for this project, not into the state file.
  5. Bump the one "Last updated" line with a few words on what changed. No chain of prior dates.
  6. Check the size. Over about 10KB, the file is first copied verbatim to archive/state-history/, then compacted.
  7. Link new artifacts. Any draft or doc created in the session gets listed under Artifacts, so nothing is orphaned.

How loops reach the tracker

The tracker is the single list of everything in flight. It has a few sections: Today, Quick Marks (my capture inbox), Waiting on Me, Waiting on Others, Project next steps (one group per state file), a Watch List, and Resolved This Week.

Every way a loop gets in

SourceWhat happens
A working sessionAt update the files, anything I committed to in the session becomes a line. Project work goes to that project's group under Project next steps.
Session logThe log's Open loops section is screened; anything not already tracked gets a line.
Meetingsprocess granola turns my to-dos into numbered lines and other people's into Waiting on Others.

Weekly scanrun open loops searches the last 7 days of email, Slack, calendar and Notion for asks I haven't answered and asks I'm waiting on.
Weekly sweepPromotes project next steps I've dated for this week into Waiting on Me.

The loop test

I stopped checking the tracker once because it filled with lines like "Office vendors you now own," which could never be ticked off. Now every line has to pass three checks before it lands:

  1. One action, starting with a verb. "Ask the vendor to confirm the install is done," not "install invoice."
  2. A done-state I'd recognize, so ticking the box means something.
  3. A date: due, by, or when to look again. If the source has none, Claude asks.

Anything that fails goes somewhere else instead of being forced in:

It's actuallyIt goes to
Several actions bundledSplit into one line each, each with its own date
Something only someone else can moveWaiting on Others, with a nudge date
An area I own, or reference infoA wiki reference page, linked from the loops it creates
Multi-step project workProject next steps, in that project's group
Waiting on a condition, not a dateWatch List, phrased "becomes a loop when..."

Keeping it clean

  • IDs. Every loop gets the next number from a counter in the tracker header, so it can be referenced from anywhere ("see #412").
  • No duplicates. When the sweep promotes an item from a project group, it stamps the original with (→ tracker #412 2026-11-17) so a re-run never adds it twice.
  • One item, one line, one file. If something already has a home, other files point to it rather than repeating it.
  • Sorted by date, earliest first. Flags (urgent, aging, stale) are shown on the line but never move it.
  • Quiet isn't resolved. A loop closes only when the ask was answered or the thing shipped.

The proposals ledger

A separate list for one specific thing: every recommendation or ask I've put (or drafted to put) in front of someone who decides. It exists because a proposal I drafted and never sent looks exactly like one waiting on my boss, unless something tracks it.

  • Statuses: proposed, sent, accepted, accepted by silence, declined, superseded, stalled, implemented, parked.
  • Every new row records its expected path, which Claude asks me for: "expect: resolved orally in the Thursday 1:1." That way a decision made out loud is never later misread as a stall.
  • Every closed row records how it closed, then moves to an archive file so the live ledger only shows what's still open.
  • Rows are added at session log time and in debriefs, and reviewed by the weekly sweep.

What happens when I log a session

Logging is separate from update the files. Updating the files keeps the vault current. A session log is a record of what we did and why, and I only ask for one when a session produced decisions or something claude.ai and Cowork need to know. At most once a day.

Why logs exist at all

  • Cross-surface handoff. The entry goes to Craft because claude.ai and Cowork can read it there. Each entry ends with a "To resume" line written as the literal first message of the next session, so any surface can pick up the work.
  • The reasoning survives. State files hold the current picture. Only the log holds why we chose it, which matters when someone later asks "why did we do it this way?"
  • It triggers the rest of the system. Logging screens the session into the wiki and the proposals ledger.

The steps, in order

  1. State file first. Claude updates the project's state file before writing anything else. The log is never the only home of live project information.
  2. Ask, don't guess. If the session produced a draft, an ask or a recommendation, Claude asks me one or two direct status questions: "Will this go to your manager as a message, or are you raising it in the 1:1?" "Unknown" is a fine answer and gets recorded as unknown. A guessed status with a question mark is not allowed.
  3. Read the template. Claude reads a "Session Log Entry Template" doc in Craft and follows it exactly.
  4. Choose light or full. Light is the default: the database fields, three lines of what we did, and one To resume line. Full, for sessions with real decisions, has six sections: Current state, Decisions and why, Artifacts and locations, Open loops, To resume, Prompts worth reusing.
  5. Write the Craft entry into a Craft database, with short fields (date, topic, category, follow-up) so the list stays scannable. The topic matches the state file's name.
  6. Mirror it into the vault as sessions/2026-11-17-hiring.md, with frontmatter that links the state file and wikilinks to people and projects in the body, so it shows up in their backlinks.
  7. Screen for the wiki. The Decisions section is checked for durable knowledge (a principle, a precedent, a fact about a policy or person). If there is some, it's folded into the wiki and logged as ingest | Session: hiring. Most light entries come back "checked, nothing new."
  8. Screen for the ledger. Any ask or recommendation put in front of a decider gets a ledger row, or a status change on its existing row, with the expected path from step 2.
  9. Append to the usage record. One line goes onto a wiki page that tracks how I use AI, so even quick sessions feed that picture.
  10. Mark superseded entries. The log is append-only, with one exception: if this session reversed a decision from an earlier entry, that entry gets a "Superseded by" note at the top.

How the wiki gets written

The wiki follows Andrej Karpathy's "LLM wiki" pattern, and the division of labor is strict: I choose sources and ask questions; Claude writes and maintains every page, link, index entry and log line. I never edit wiki pages by hand. If I want something changed, I leave a line starting ASHLEY: on the page, and Claude acts on it and removes it.

Three layers

  1. Raw sources that are never modified: clipped articles in wiki/raw/, plus meeting notes, reference docs and session mirrors, which are cited in place.
  2. The pages Claude writes, in four folders: sources/ (one summary per ingested source), concepts/ (ideas, frameworks, recurring principles), entities/ (people, organizations, tools), and syntheses/ (answers worth keeping, like comparisons and analyses).
  3. The schema, wiki/CLAUDE.md: the rules for ingesting, querying and linting. When we agree on a change, it's written here in the same session.

What happens on ingest

Triggered by ingest this: reference/policy.md, by processing a meeting, or by the session-log screen. If I forget, the weekly sweep lists new reference files the wiki hasn't seen yet and asks whether to ingest them.

  1. Read the source in full. For anything ambiguous or high-stakes, Claude tells me the key takeaways first and checks the emphasis.
  2. Write a source page summarizing it (optional for meeting notes, which are already the cited source).
  3. Update every affected page. One source often touches many concept and entity pages, and that's expected.
  4. Flag contradictions, never overwrite. If a new source disagrees with a page, both versions stay under a ### Contradiction heading with dates and sources.
  5. Update the index. index.md lists every page once with a one-line summary. Queries start there, so it has to be accurate.
  6. Write a log entry in log.md listing pages created and changed.

wiki/log.md (one entry)

## [2026-11-17] ingest | Meetings: Manager 1:1
- [[Manager Name]]: one Working with them bullet
  (prefers a one-page summary for hiring plans).
- [[Company Levels]]: added the precedent for this role type.
- Checked, nothing new: [[Recruiter Name]].

Questions and upkeep

  • wiki: what's our precedent for X? Claude reads the index, then the relevant pages, and answers with citations. If the answer is worth keeping, it offers to save it as a synthesis page.
  • lint the wiki (monthly) checks for contradictions, stale claims, orphan pages with no links in, links to pages that don't exist yet but probably should, and index drift. Mechanical fixes are applied; judgment calls come back to me.
  • Every claim cites its source, so I can always check where a "fact" came from.

How person pages get updated

Each person I work with closely has an entity page, and its most important section is Working with them: how they decide, what framing lands, what they ask for first, how they react under pressure, and verbatim lines that show how they think. One dated bullet per insight, each with a citation.

CLAUDE.md keeps only one line per stakeholder and points to their page. Before drafting anything for one of them, or recommending how to approach them, Claude reads that section.

Five ways a page gets a new bullet

  1. Every processed meeting gets a people pass over its attendees, even when nothing was decided. A status sync still shows how someone weighs things. If the meeting only confirmed what the page already says, the note records "checked, nothing new" instead of a duplicate. A recurring stakeholder with no page gets one created from the template.
  2. Debriefs. If I say "they pushed back until I framed it as a cost saving," that goes on their page.
  3. The weekly open loops scan reads Slack and email threads for loops anyway, so it also captures how people work from those same threads, without widening the search.
  4. refresh [name]'s page from Slack reads my recent DMs with that person and adds anything new. I run it before high-stakes conversations: development chats, comp asks, hard 1:1s.
  5. Session logs, when a session showed something new about how someone decides.

Over a few months these pages become the most useful thing in the vault. Claude can predict which framing will land with whom, and it's citing evidence rather than guessing.

How concepts get written

A concept page holds an idea that keeps coming up: a framework, a company norm, a principle, a recurring pattern. Concept pages come from four places:

  • An ingested source introduces or defines one, like a levels guide or a handbook policy.
  • A decision sets a principle. When a meeting or session settles a precedent, the principle gets its own page so it isn't relitigated.
  • A correction becomes a rule. When I correct Claude in a way that generalizes, the lesson can become a concept. An example from my wiki: "Absence Is Not Evidence" exists because an automated review once concluded I'd never sent a message, since it couldn't find my draft text in Slack. In fact I'd rewritten and sent it, and a long thread had followed. The page records the failure and the rules that came out of it.
  • Lint finds a gap. An idea linked from many pages but with no page of its own gets proposed as a new concept.

Every concept page follows the same template:

# Concept Name
One-line definition.

## In plain terms
An explanation a smart reader with zero context could follow.

## Why it matters here
Its relevance to my actual work. Concrete, not generic.

## Related
- [[Other Page]]: one line on how they connect.

## Sources
- [[Where this came from]]

Concepts get updated the same way as everything else: a new source that adds to or contradicts one gets folded in with a citation, and contradictions are kept side by side.

The weekly sweep and NOW

On Mondays I say run open loops. It scans email, Slack, calendar and Notion for the past week, updates the tracker, does the context pass (project facts to state files, people insight to wiki pages), flags aging and stale loops, and drafts nudges for me to adapt. Then it runs the state sweep, which has five phases:

  1. Read and harvest. NOW's priorities first, then the tracker, ledger and every state file. Process ticked boxes and Notes sections, then collect every unchecked action across all state files.
  2. Reconcile. Match items across files and build a list of duplicates and disagreements: dates that passed, ledger rows quiet for two weeks, state files untouched for three weeks, new reference files the wiki hasn't seen.
  3. Triage with me. One short table of only what's new or changed, each stalled-looking item phrased as "did this happen in some form?" I answer in shorthand ("3 done orally," "7 park to Dec," "12 dead").
  4. Route and apply. Update every affected file, move closed ledger rows to the archive, promote this week's project steps into the tracker with markers, and move drafts older than 30 days to an archive folder.
  5. Rebuild NOW. Everything below my This quarter section is regenerated: Top 3, This week, Waiting on others, Desk work by project, Can wait, Parked.

NOW is a view, not a source. Every line in it points back to a state file, tracker line or ledger row, so it can never drift into a second version of the truth. The one section I own is This quarter: my priorities, capacity and what I've dropped. The sweep never rewrites it. If it finds something that contradicts my priorities, it asks. Whenever This quarter changes, Claude copies it to the Craft context hub so claude.ai and Cowork see the same priorities.

Rules that made it work

Most of these came from something breaking once.

  • A ticked box anywhere means done. Claude reconciles everywhere else that item lives on its next touch. That makes my phone a full input device.
  • Capture without Claude. Notes sections and Quick Marks are landing zones that get folded in and emptied, never left as archives.
  • No draft doesn't mean not done. I close most things out loud or in threads, and I rarely send a draft word for word. Claude never treats a missing artifact as proof a loop is open, and asks instead.
  • Views are rebuilt, homes are edited. NOW is regenerated, so it can't become a second source of truth.
  • One fact, one home. Everything else points to it.
  • Never delete, always archive. Old state files, closed ledger rows and aged drafts move to archive/.
  • Rules carry dates. When two instructions seem to conflict, the newer one wins, and the date tells Claude which that is.
  • Corrections compound. When I correct Claude, the file holding the wrong version gets fixed in the same turn, and the lesson goes into memory, a skill, or the wiki.
  • Only I read the vault. Nothing is filtered on the way in. Filtering happens when something leaves it for Notion, Slack, email or a deck. The one exception is survey responses, which stay anonymous everywhere.

Starting your own

Don't build all of this at once. Mine grew over about four months, and plenty of early structure was later folded in or retired. A version that delivers most of the value in a week:

  1. A folder with a CLAUDE.md that says "read NOW.md and tracker.md before anything else," and defines two phrases: "where do things stand?" and "update the files."
  2. A one-page NOW.md with your priorities in your own words.
  3. A tracker.md with checkboxes: one action, one person, one date per line.
  4. A state file template, and one state file per active project, written as snapshots.
  5. The habit: open every session with "where do things stand?" and close it with "update the files."

Then add pieces as you feel the need:

  • Add the wiki when you notice you're re-explaining the same people or policies.
  • Add session logs once you work across more than one Claude app.
  • Add a proposals ledger once you lose track of what you've asked your boss for.
  • Turn something into a skill once you've done it the same way three times.
  • Write a rule down every time you correct Claude about the same thing twice.
Tools in this setup: Claude Code in VS Code, Obsidian with Obsidian Sync, Craft, Notion, Granola, and Claude connectors for Slack, email, calendar and Notion. Names and examples on this page are illustrative.
